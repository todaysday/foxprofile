## Последние указания пользователя включены

1. **Устойчивость форка при обновлении upstream:** сохранять текущую панель/каталог/данные браузеров, изолировать новые модули, не копировать целиком upstream-классы, проверять конечный набор точек интеграции.
2. **Приоритет правил:** `Pragmatic DDD (DAO/DTO) → SRP → KISS/YAGNI → DRY`. Разделять реальные ответственности; не создавать слои и абстракции ради схемы.
3. **Развёртывание и приёмка на живом — последний отдельный слайс другого агента.** Основной исполнитель заканчивает слайсы 1–8 и передачу артефактов. Только отдельный deployment-агент выполняет слайс 9.

## Как передать пакет исполнителю

1. Подготовить локальный checkout своего форка. Пакет не создаёт удалённый fork и не меняет серверы.
2. Перенести каталог `openspec/changes/add-multi-user-manual-browser-workflow/` из архива в `openspec/changes/` форка. Не перезаписывать существующий change с таким именем: сначала сравнить содержимое.
3. Если `openspec/config.yaml` отсутствует, использовать приложенный. Если уже есть — объединить контекст и правила, сохранив настройки проекта. Файлы README/AGENTS самого репозитория не заменять этим README.
4. Если OpenSpec ещё не инициализирован, выполнить `openspec init` в форке с нужной интеграцией агента, затем перенести/объединить пакет. Рекомендуется использовать ту же версию CLI, на которой пакет проверен; результат проверки указан в [VALIDATION.md](VALIDATION.md).
5. Запустить из корня форка:

```bash
openspec validate add-multi-user-manual-browser-workflow --type change --strict --no-interactive
openspec status --change add-multi-user-manual-browser-workflow
```

6. Передать coding-агенту [IMPLEMENTATION_PROMPT.md](IMPLEMENTATION_PROMPT.md). После слайса 8 передать результаты отдельному агенту вместе с [DEPLOYMENT_AGENT_PROMPT.md](DEPLOYMENT_AGENT_PROMPT.md).

CLI можно установить стандартным способом OpenSpec. Пакет проверяется без запуска FoxProfile; проверка структуры не означает, что будущая реализация или работа на VPS уже принята.

## Ключевые решения

- Сохранить текущий JSON-каталог и каталоги браузеров; добавить локальный неизменяемый ID и SQLite-sidecar для новых сущностей. Не переписывать хранилище ради ролей.
- Расширить существующий `VirtualDisplay` и очистку процессов. В проверенной версии уже подтверждены `humanize=True` и `page.mouse.click(x, y)`.
- Атомарный массовый admission реализовать на сервере: текущий fan-out одиночных запусков не обеспечивает требуемой семантики.
- При HTTP timeout запуска не освобождать место, если браузер ещё стартует; при stop освобождать только после подтверждённого завершения процесса.
- Включить browser-backed cookie helper в общий учёт, сохранив существующие ограничения операций на работающих профилях.
- Первую noVNC-интеграцию ограничить Camoufox; существующие Chrome-профили сохраняют обычные операции, права и общий лимит.
- Закрытие noVNC не сообщает агенту «готово», не проверяет CAPTCHA и не возобновляет автоматизацию.
- Полный ручной браузерный ввод не должен раскрывать соседние каталоги/служебные секреты через native file access; это проверяется отдельно от REST ACL.

- `proposal.md` — причина, объём, влияние и границы.
- `design.md` — решения, точки интеграции, данные, lifecycle и обновление upstream.

- `specs/*/spec.md` — формальные SHALL-требования и сценарии.
- `references/upstream-audit.md` — аудит реальных исходников с ссылками на закреплённый commit.
- `references/api-contract.md` — предлагаемые DTO, endpoints и ошибки.
- `references/acceptance-plan.md` и `requirements-traceability.md` — приёмка и связь с источниками.
- `references/implementation-handoff.md` — единый отчёт реализации: проверенные offline-результаты, версии, входы развёртывания и оставшиеся release gates.
- `references/upstream-update.md` — подготовка обновлений и финальное продвижение отдельным агентом.
- `references/inputs/` — три неизменённых исходных документа.
- `slices/09-live-deployment-and-acceptance.md` — автономное задание deployment-агенту.
- `VALIDATION.md`, `MANIFEST.sha256` — результаты проверки пакета и контрольные суммы.

Новые endpoints и имена расширения в design — проектные контракты. Реальные существующие функции перечислены отдельно в source audit. Гарантия бесконфликтного обновления на любую будущую версию upstream не заявляется: предусмотрены небольшие изменения и проверка совместимости до развёртывания.
