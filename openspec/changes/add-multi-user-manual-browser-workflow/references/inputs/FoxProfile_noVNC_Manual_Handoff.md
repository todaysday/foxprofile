# FoxProfile + Camoufox: noVNC внутри обычного экрана управления

**Версия:** 1.1  
**Дата:** 2026-11-04  
**Статус:** рабочая спецификация доработки с уточнёнными границами задачи; реализация и нагрузочные испытания не выполнены.  
**Назначение:** передать разработчику или coding-агенту принятые решения без повторного обсуждения хостингов и установки браузера.

> В обычном экране управления FoxProfile добавить кнопку **«Открыть в noVNC»**. Она показывает тот же работающий браузер, но с полноценным ручным вводом. Кнопка **«Вернуться назад»** отключает noVNC, освобождает временный VNC-сеанс и возвращает обычный экран управления. **Кнопка ничего не отправляет агенту и не возобновляет автоматизацию.** Пользователь сам сообщает агенту «готово» в их обычном диалоге.

## 1. Исходные условия и границы задачи

У пользователя уже есть серверы и установлен Camoufox. Рассматриваются Oracle Free Tier на ARM64 и AMD-хостинг на x86-64. **На обоих серверах нет GPU.** Сравнивать тарифы, переустанавливать систему или писать инструкцию по покупке сервера не требуется.

Целевой масштаб — около **100 сохранённых профилей** и **до 10 одновременно работающих браузеров** в рассматриваемом пуле. Это не требование держать все профили открытыми. Профили, cookies, настройки отпечатка и прокси должны оставаться раздельными.

Основной менеджер — **FoxProfile**. Обычное ручное управление через его панель и действия агента через существующий API сохраняются. noVNC нужен как дополнительный режим для редких действий, которые неудобно или невозможно выполнить отдельными кликами: удержание кнопки мыши, перетаскивание, взаимодействие со сложным элементом интерфейса или ручное прохождение проверки.

В первой реализации достаточно **одного одновременно активного ручного VNC-сеанса на управляемый экземпляр системы**. Остальные браузеры продолжают свои задачи. Распределённый планировщик между двумя серверами не входит в эту доработку; идентификатор хоста необходимо учитывать, чтобы не перепутать локальные номера дисплеев.

## 2. Почему сохраняем FoxProfile и что уже подтверждено

Пользователь проверил свою реализацию FoxProfile и подтвердил:

| Место | Подтверждённый фрагмент | Значение для решения |
|---|---|---|
| `control.py` | `page.mouse.click(x, y)` | REST-клик выполняется через mouse API Playwright, а не через JavaScript `element.click()` |
| `runner.py` | `"humanize": True` | Гуманизация включена при запуске Camoufox |

Это **проверка пользователя для его кода**, а не утверждение, что любая версия FoxProfile содержит эти строки. Перед реализацией зафиксировать установленную ревизию и сохранить существующее поведение.

В Playwright `mouse.click()` состоит из перемещения, нажатия и отпускания кнопки. Отдельные `down()`, `move()` и `up()` также существуют, но одиночный `click()` не заменяет непрерывное перетаскивание. [S1]

Camoufox предоставляет встроенную гуманизацию движения курсора. Поэтому обычные клики панели и автоматизации, проходящие через этот же механизм, не требуют дополнительного собственного генератора траекторий. **Это не означает идентичность пауз, ввода текста и всего поведения пользователя и агента.** [S2]

### Важное отличие noVNC

noVNC — другой канал ввода: человек управляет X-дисплеем через VNC, а не отправляет REST-клики в Playwright. **Нельзя обещать, что `humanize=True` будет дополнительно обрабатывать эти ручные движения.** В этом режиме путь мыши задаёт сам человек.

Таким образом, решение сохраняет один браузер, профиль и страницу, но сознательно допускает два способа ввода: обычный REST/Playwright и временный ручной VNC. Собственную реализацию drag-and-drop поверх REST в первой версии не делаем.

## 3. Архитектура: подключаем просмотр, а не переносим браузер

```text
Сохранённые профили: около 100
            │
            ▼
Активный пул: до 10 браузеров Camoufox
            │
            ├── профиль pin-017 → экземпляр A → X-дисплей A
            ├── профиль pin-042 → экземпляр B → X-дисплей B
            ├── профиль pin-063 → экземпляр C → X-дисплей C
            └── ...

Обычный экран управления FoxProfile для pin-042
            │
            ├── обычный режим → существующий REST/Playwright
            │
            └── «Открыть в noVNC»
                       │
                       ▼
                 noVNC в этой же панели
                       │ WebSocket
                       ▼
                авторизованный шлюз
                       │
                       ▼
                временный VNC-сервер
                       │
                       ▼
             существующий X-дисплей B
                       │
                       ▼
             тот же Camoufox, экземпляр B
```

**Не создаётся одиннадцатый браузер или отдельный рабочий стол для человека.** Не копируются cookies, не переносится профиль, не выполняется повторный вход. Переключается только способ управления уже открытым браузером.

x11vnc подходит как первоначальный адаптер: он умеет подключаться к существующему X-дисплею. Доступ к дисплею зависит от локальных прав и, при использовании X11-авторизации, от Xauthority. [S3]

### Режим запуска браузеров

Все браузеры, которым может потребоваться ручная помощь, должны **с самого начала** работать на доступном виртуальном X-дисплее. Документированный режим Camoufox — `headless="virtual"`, создающий виртуальный дисплей в фоне. [S4]

Предпочтительный порядок интеграции:

1. Использовать уже создаваемый FoxProfile/Camoufox виртуальный дисплей и сохранить его параметры в данных активного запуска.
2. Если текущая интеграция не даёт надёжно получить этот дисплей, доработать запуск: менеджер явно выделяет Xvfb, а графический Camoufox запускается на нём. Конкретный способ передачи `DISPLAY` проверить на установленной версии.

Это альтернативы, а не два слоя Xvfb одновременно. Не менять рабочую схему запуска без необходимости и не копировать непроверенные параметры Python API из предыдущего обсуждения.

**Настоящий `headless=True` не является целевым режимом этого решения.** Подключение к уже существующему экрану предполагает, что такой экран был создан при запуске. Переходить из настоящего headless в графический режим ради ручной помощи не планируется.

Десять слотов — логическая модель параллельности. Не обязательно заранее создавать десять постоянных Xvfb: допустимо создавать дисплей вместе с браузером и освобождать вместе с ним. До завершения ручной помощи дисплей и браузер должны сохраняться.

## 4. Профили, дисплеи и неизменность окружения

Настройки идентичности принадлежат **профилю**, а не номеру слота: постоянная директория, прокси, сохранённые параметры отпечатка, язык, часовой пояс и геометрия браузера. noVNC-интеграция не должна заново генерировать или менять их.

Нельзя одновременно запускать один и тот же профиль в двух слотах. Слот с работающим браузером нельзя отдать другому профилю; открытый ручной сеанс не должен переживать завершение или замену этого запуска браузера.

Для новых профилей базовый размер виртуального экрана можно принять **1366×768**; **1920×1080 не является требованием**. Уже используемую согласованную геометрию не менять автоматически. Размер X-дисплея, окно браузера и видимые странице параметры экрана — связанные, но не тождественные величины; их согласованность проверяется отдельно.

При открытии noVNC масштабировать изображение **на стороне клиента**, а не менять удалённое разрешение. В API noVNC для этого предусмотрены `scaleViewport` и `resizeSession`. [S5]

```javascript
// Фрагмент настройки уже созданного объекта RFB, не полный код интеграции.
rfb.scaleViewport = true;
rfb.resizeSession = false;
rfb.viewOnly = false;
```

Архитектура одинакова для ARM64 и x86-64, но это не обещание одинакового графического отпечатка между хостами. Перенос профилей между архитектурами и настройка WebGL/Canvas не входят в этот патч. Отсутствие GPU не компенсируется выдуманным названием видеокарты.

## 5. Интерфейс: кнопка внутри обычного управления

Кнопка размещается **не только в списке профилей**, а непосредственно над изображением страницы в уже открытом экране управления конкретным профилем.

### Обычный режим

```text
Управление · pin-042                         [Открыть в noVNC]

┌─────────────────────────────────────────────────────────┐
│ Текущее изображение страницы                            │
│ Существующие клики и ввод через FoxProfile               │
└─────────────────────────────────────────────────────────┘
```

### Полное ручное управление

```text
Полное управление · pin-042                 [Вернуться назад]

┌─────────────────────────────────────────────────────────┐
│ Встроенный noVNC                                        │
│ Удержание кнопки, перетаскивание, мышь и клавиатура       │
└─────────────────────────────────────────────────────────┘
```

noVNC заменяет область просмотра **в том же экране**. Новая вкладка и повторный выбор профиля не нужны. Можно встроить библиотеку RFB либо готовую `vnc.html`; оба варианта предусмотрены документацией noVNC. [S5][S6]

На время noVNC отключить в этой панели обычные REST-обработчики мыши и клавиатуры, а обновление скрытого изображения приостановить. Не должно быть двойной отправки одного действия двумя каналами.

### Семантика «Вернуться назад»

Это одно пользовательское действие, которое:

- прекращает VNC-ввод, закрывает соединение и освобождает временный VNC-сеанс;
- возвращает обычную область просмотра со свежим изображением;
- возвращает существующие обработчики обычного ручного управления панели.

**На этом действие кнопки заканчивается.** Она не отправляет «готово» агенту, не проверяет прохождение CAPTCHA, не переключает состояние задачи агента и не запускает автоматизацию. Её поведение не зависит от того, ожидает ли какой-либо агент помощи.

После возврата пользователь может продолжить работу через обычную панель. Сообщение агенту остаётся обычным сообщением пользователя, а не функцией кнопки.

## 6. Агент остаётся вне интеграции noVNC

Контекст использования: агент сам прекращает действия с нужным браузером и говорит пользователю: «Пройди проверку и скажи мне, когда готово». Это существующее взаимодействие человека и агента, а не новая функция FoxProfile.

```text
Агент просит ручную помощь и ждёт ответа пользователя
    ↓
Пользователь: обычное управление → «Открыть в noVNC»
    ↓
Пользователь выполняет ручное действие
    ↓
Пользователь нажимает «Вернуться назад»
    ↓
noVNC отключается; возвращается обычный экран управления
    ↓
Пользователь сам пишет агенту «готово» в обычном диалоге
```

**Доработка заканчивается на возврате обычного экрана управления.** Она не должна доставлять ответы агенту или задавать, как тот проверяет результат и продолжает свою работу.

Не добавлять адаптер сообщений агенту, события `human_input_completed`, идентификаторы запросов помощи, обработчики возобновления или отдельную систему Pause/Resume. FoxProfile не обязан знать, какой агент ожидает ответа.

В этом сценарии агент уже ожидает пользователя, поэтому кнопке не нужно останавливать его. Во время ручного ввода пользователь и агент не должны одновременно выполнять действия в одном браузере; это условие существующего рабочего процесса, а не основание расширять данный патч до оркестрации агента.

## 7. Минимальная серверная доработка

Понадобятся три компонента внутри существующей системы, без интеграции с агентом и без отдельного универсального оркестратора.

| Компонент | Ответственность |
|---|---|
| Данные активного запуска | Связь профиля, хоста, конкретного запуска браузера и его X-дисплея |
| Менеджер ручного сеанса | Запуск временного VNC-сервера, проверка доступности, завершение и очистка |
| Авторизованный WebSocket-шлюз | Соединение noVNC только с разрешённым сеансом |

### Идентификаторы

```text
host_id           — сервер, на котором работает браузер
profile_id        — постоянный профиль
browser_run_id    — уникальный идентификатор текущего запуска браузера
slot_id           — текущий слот, если такая сущность уже есть
DISPLAY           — реальный X-дисплей этого запуска
XAUTHORITY        — путь к авторизации X11, если она используется
manual_session_id — временный VNC-сеанс
```

`DISPLAY` и `slot_id` могут повторно использоваться. Поэтому проверять только их недостаточно: старый ручной сеанс не должен внезапно подключить человека к другому браузеру, занявшему тот же слот. Связь с `browser_run_id` проверяется при открытии, переподключении и завершении.

VNC-сервер должен иметь доступ именно к X-сокету нужного процесса. При контейнерном размещении учитывать namespace и права: совпадение строки `:101` в разных контейнерах не означает один и тот же экран.

### Предлагаемый контракт API

Имена ниже — **предложение для новой доработки**, а не существующие эндпоинты FoxProfile. Их следует адаптировать к структуре проекта.

| Операция | Назначение |
|---|---|
| `POST /profiles/{profile_id}/manual-sessions` | Проверить активный запуск и права, открыть ручной VNC-сеанс |
| `GET /manual-sessions/{session_id}` | Получить состояние ручного сеанса |
| `DELETE /manual-sessions/{session_id}` | Закрыть ручной сеанс и освободить временные ресурсы; вызывается кнопкой «Вернуться назад» |
| WebSocket сеанса | Передавать VNC-трафик после серверной авторизации |

Backend самостоятельно определяет `DISPLAY`, порт и процесс по активному запуску. Клиент не передаёт произвольный адрес VNC-сервера или номер дисплея.

Отдельный эндпоинт `/complete` с подтверждением задачи агента не нужен. Создание и закрытие VNC-сеанса не связано с запросами или сеансами агента.

### Порядок закрытия

Сервер проверяет принадлежность сеанса, запрещает дальнейший ручной ввод, отзывает доступ, закрывает соединение и освобождает временный VNC-процесс. Затем панель восстанавливает обычное управление и получает свежее изображение страницы.

Завершать нужно временный VNC-процесс, **не Camoufox и не Xvfb**. Повторное закрытие уже закрытого сеанса должно быть безопасным и не затрагивать новый сеанс или другой профиль. Никакие сообщения агенту при этом не создаются.

## 8. Ошибки, гонки и отключения

| Ситуация | Требуемое поведение |
|---|---|
| Пользователь дважды нажал «Открыть в noVNC» | Вернуть тот же действующий сеанс или корректно отклонить дубль; не создавать два VNC-сервера |
| Уже открыт ручной сеанс другого профиля | Показать, какой профиль занят; не переключать дисплей незаметно |
| Вкладка закрылась, пропала сеть или соединение истекло | Закрыть/ограничить ручной доступ и очистить временные ресурсы; не отправлять сообщений агенту и не менять его задачу |
| Соединение восстановилось | Подключить к тому же актуальному запуску после повторной авторизации; при завершённом сеансе открыть новый |
| Браузер завершился или слот был переиспользован | Аннулировать старую привязку; не подключаться к новому профилю по старому дисплею |
| «Вернуться назад» нажата повторно | Безопасно вернуть состояние закрытого сеанса; не завершать чужой или новый сеанс |
| После ручного действия проверка осталась на странице | Не объявлять успех и не закрывать задачу; результат проверки не входит в обязанности noVNC-интеграции |

При штатном завершении и потере соединения проверить освобождение зажатых кнопок и клавиш. После VNC обязательна проверка следующего Playwright-клика: ручной ввод не должен оставлять браузер в состоянии перетаскивания или приводить к неожиданному поведению курсора.

Не добавлять управление жизненным циклом агента под видом обработки ошибок VNC. Открытие, возврат, тайм-аут и обрыв соединения затрагивают только ручной сеанс и интерфейс панели.

## 9. Безопасность доступа

VNC даёт полный ручной доступ к выбранному браузеру, поэтому требования относятся к самой интеграции, а не к CAPTCHA.

Использовать существующую авторизацию панели и проверять права на профиль при создании сеанса и WebSocket-подключении. Публичный доступ — через защищённый HTTPS/WSS-шлюз; сам VNC-порт не выставлять в интернет. Для локального x11vnc предусмотрено ограничение входящих подключений локальной машиной. [S3]

Временный доступ привязывать к пользователю, профилю и запуску браузера. После завершения отзывать его. Не помещать постоянные пароли, cookies или VNC-секреты в обычные URL и журналы. Для cookie-аутентификации предусмотреть проверки Origin и защиту изменяющих состояние запросов.

Запускать дочерний VNC-процесс без shell-конкатенации пользовательских значений. Не отключать авторизацию X11 глобально ради подключения. Не включать ненужные возможности вроде передачи файлов и не публиковать соседние дисплеи.

В доступном README x11vnc есть предупреждение об отсутствии активного сопровождения проекта. Поэтому используемая сборка и её сопровождение должны быть проверены при внедрении; VNC-адаптер следует оставить заменяемым. [S3]

## 10. Память и жизненный цикл ресурсов

Целевая схема **не требует десяти постоянно работающих VNC-серверов**:

| Ресурс | Количество в целевой схеме |
|---|---|
| Сохранённые профили | Около 100 на диске |
| Активные браузеры | До 10 |
| Виртуальные дисплеи | По активным браузерам; при собственном пуле — не более его ёмкости |
| Временные VNC-сеансы | 0 обычно, 1 во время ручной помощи |
| Дополнительный браузер для человека | 0 |

Бюджет для измерения:

```text
RAM сервера = ОС и службы
            + FoxProfile / агент / API
            + активные деревья процессов Camoufox
            + активные виртуальные дисплеи
            + временный VNC-сервер и WebSocket-шлюз
```

Сам веб-клиент noVNC работает на устройстве пользователя; серверу нужны VNC-сервер и канал передачи. Архитектура веб-клиента описана в документации noVNC. [S5][S6]

Ранее обсуждавшиеся диапазоны памяти на браузер и ориентир в 16 ГБ **не были замерами этой установки** и не являются обязательным требованием. Точный расход зависит от страниц, числа вкладок, длительности работы и других служб. В этой спецификации не утверждается, что FoxProfile измеренно экономнее другого менеджера на конкретное число мегабайт.

При внедрении измерить одинаковые сценарии: 1, 5 и 10 браузеров; затем те же нагрузки с одним подключённым noVNC и после его закрытия. Проверять пиковую память, CPU, отзывчивость ручного ввода и отсутствие накопления временных процессов. Размер экрана 1366×768 — выбранный базовый вариант, а не обещание многогигабайтной экономии.

## 11. Порядок внедрения

1. **Проверить текущую установку.** Зафиксировать ревизии FoxProfile/Camoufox, существующий режим запуска и способ получения X-дисплея. Сохранить подтверждённые `page.mouse.click()` и `humanize=True`.
2. **Сделать подключение к одному тестовому профилю.** Без перезапуска браузера показать его существующий дисплей через временный VNC-сервер; проверить обычный тестовый drag-and-drop.
3. **Встроить переключение в панель.** Обычная область управления ↔ noVNC, без новых вкладок и изменения геометрии удалённого экрана.
4. **Реализовать возврат и очистку.** «Вернуться назад» закрывает VNC-сеанс и восстанавливает обычное управление. Проверить повторные нажатия, обрывы соединения и отсутствие сообщений агенту.
5. **Проверить параллельную работу.** Несколько профилей, один ручной сеанс, отсутствие влияния на соседние браузеры; затем повторить проверку на обоих хостах.

Не добавлять интеграцию с агентом, новое хранилище сообщений, очередь, собственный протокол перетаскивания или полноценный desktop environment без конкретной необходимости. Не проводить массовую перенастройку отпечатков в рамках этой задачи.

## 12. Критерии приёмки

| № | Проверка | Ожидаемый результат |
|---|---|---|
| 1 | Открыть noVNC из обычного управления | Показан выбранный профиль внутри того же экрана |
| 2 | Сравнить запуск до и после подключения | `browser_run_id` не изменился; браузер и вкладка не перезапущены |
| 3 | Выполнить ручное перетаскивание | Нажатие, удержание, движение и отпускание работают на тестовой странице |
| 4 | Нажать «Вернуться назад» | Ручной VNC-доступ закрыт, обычный экран и его существующее управление восстановлены |
| 5 | Проверить отсутствие интеграции с агентом | Открытие и закрытие noVNC не отправляют «готово», не проверяют результат CAPTCHA и не возобновляют автоматизацию |
| 6 | Просто оборвать соединение | Выполняется очистка ручного сеанса; сообщения и команды агенту не создаются |
| 7 | Дважды нажать кнопку возврата | Нет ошибок, лишних процессов или завершения другого сеанса |
| 8 | Проверить остальные активные профили | Они не перезапускаются и не теряют управление |
| 9 | Перезапустить браузер при старом VNC-сеансе | Старый сеанс не подключается к новому запуску или соседнему профилю |
| 10 | Проверить разрешение, окно и профиль | Открытие/закрытие noVNC не меняет сохранённые настройки и геометрию |
| 11 | Выполнить Playwright-клик после ручного режима | Нет зажатых клавиш/кнопок и некорректного продолжения drag-жеста |
| 12 | Проверить очистку и авторизацию | Временный VNC-процесс освобождён, старый доступ отозван, чужой профиль недоступен |
| 13 | Повторить на ARM64 и x86-64 без GPU | Работает тот же пользовательский сценарий; фактические ресурсы измерены отдельно |
