# FoxProfile: пользователи, администраторы и доступ к профилям

**Версия:** 0.2  
**Статус:** техническое задание на доработку  
**Проект:** Pinterest-ферма на VPS  
**Целевая система:** существующая установка и веб-панель FoxProfile (`chienbm98/foxprofile`)

## 1. Цель и основание документа

Добавить в существующую панель FoxProfile двухролевую модель доступа, разделение браузерных профилей между пользователями и общий серверный лимит одновременно активных профилей — по умолчанию **10**.

**Основной принцип: пользователь имеет полный контроль над своими / назначенными ему профилями. Администратор управляет всеми профилями, пользователями и глобальными настройками системы.**

Общий лимит действует для всех пользователей, администратора и служебного агента суммарно; административная роль не позволяет обходить его.

Не создавать новую панель или второй менеджер браузеров. Доработать существующий интерфейс: фильтровать профили, показывать административные разделы только администратору и проверять те же ограничения на сервере.

Документ фиксирует требования из обсуждения. Он не является аудитом текущего исходного кода FoxProfile и не утверждает, что перечисленные функции уже реализованы. Перед изменениями исполнитель должен проверить фактическую структуру проекта, существующие механизмы авторизации и доступные операции. Имена сущностей ниже — проектные обозначения, а не подтверждённые имена файлов, таблиц или API.

## 2. Согласованные требования

### 2.1. Роли

Нужны только две роли:

- **Администратор (`admin`)** — все профили, управление пользователями и назначениями, глобальные настройки, конфигурация MCP и служебного API-доступа.
- **Пользователь (`user`)** — полный набор существующих операций со своими / назначенными профилями, без доступа к чужим профилям и глобальным настройкам.

Отдельные роли «оператор» и «наблюдатель», конструктор разрешений и права на каждую кнопку не требуются.

### 2.2. Матрица доступа

| Операция | Администратор | Пользователь |
|---|---|---|
| Просматривать список профилей и их состояние | Все | Только свои / назначенные |
| Запускать и останавливать профиль | Любой | Свой / назначенный |
| Открывать Viewer уже запущенного профиля | Любого профиля | Своего / назначенного |
| Кликать, вводить текст, прокручивать страницу, вручную проходить капчу | В любом профиле | В своём / назначенном |
| Использовать существующие средства навигации и управления вкладками | В любом профиле | В своём / назначенном |
| Изменять настройки профиля | Любого | Своего / назначенного |
| Изменять прокси профиля | Любого | Своего / назначенного |
| Изменять fingerprint и доступные параметры окружения профиля | Любого | Своего / назначенного |
| Импортировать и экспортировать cookies | Любого | Своего / назначенного |
| Удалять профиль | Любой | Свой / назначенный |
| Выполнять массовые операции | Над всеми профилями | Только над своими / назначенными |
| Создавать пользователей, менять роли и отключать доступ | Да | Нет |
| Назначать профили пользователям и отзывать назначения | Да | Нет |
| Менять глобальные настройки сервера и MCP | Да | Нет |
| Менять общий лимит одновременно активных профилей | Да | Нет |
| Просматривать и менять служебные ключи общего доступа | Да | Нет |

Разрешение относится ко всему профилю: назначение профиля пользователю даёт ему полный контроль над ним, включая изменение fingerprint, экспорт cookies и удаление. Не добавлять скрытых ограничений «можно работать, но нельзя менять настройки».

Не имеет значения, кто запустил профиль: администратор, пользователь или агент. Пользователь с доступом к этому профилю должен иметь возможность открыть его уже работающий Viewer. При этом сохраняются обычные ограничения FoxProfile для операций, требующих остановленного браузера.

### 2.3. Рабочие допущения для первой реализации

Следующие пункты предложены как минимальные правила реализации; отдельно пользователем они не детализировались:

1. Пользователь может создавать новые профили. Созданный им профиль автоматически назначается ему.
2. Если существующая система поддерживает клонирование или импорт полного профиля, пользователь может выполнять эти операции. Новый профиль автоматически назначается создавшему / импортировавшему его пользователю.
3. Если существующая система поддерживает экспорт полного профиля, он разрешён пользователю для его профилей, как и экспорт cookies.
4. Новые пользователи не получают доступ к существующим профилям автоматически.
5. Администратор может назначать существующие профили пользователям. Интерфейс совместного владения несколькими пользователями не обязателен для первой версии.
6. При отключении пользователя его профили сохраняются и остаются доступными администратору.

Не реализовывать отсутствующий у FoxProfile экспорт, клонирование или другой браузерный функционал только ради этого задания: задача — разграничить доступ к существующим возможностям.

### 2.4. Общий лимит одновременно активных профилей

**Согласованное значение по умолчанию — 10 профилей на всю установку FoxProfile.** Это не лимит на каждого пользователя и не ограничение числа сохранённых профилей.

Проектное имя параметра: `max_concurrent_profiles`. Значение — целое число не меньше 1; `0`, отрицательные и нецелые значения недопустимы. Если настройка ещё не сохранена, применяется **10**. Изменять значение может только администратор; настройка сохраняется после перезапуска сервиса и VPS. Это требование к доработке, а не утверждение о наличии такого параметра в текущем FoxProfile.

**Что занимает место:** профиль с зарезервированным запуском, запускающийся или работающий профиль. Останавливающийся профиль продолжает занимать место до подтверждённого завершения его браузерной сессии. Один профиль занимает одно место, независимо от количества вкладок, процессов браузера, подключений Viewer и клиентов управления.

**Что не занимает новое место:** хранение остановленного профиля, создание / импорт профиля без запуска, открытие Viewer уже запущенного профиля и подключение агента к той же сессии. При заполненном лимите пользователь по-прежнему может открыть свой работающий профиль и вручную пройти капчу.

Правила применения:

1. Все способы запуска используют один серверный ограничитель: панель, REST API, MCP, массовые операции и любые существующие фоновые или автоматические запуски. Отдельный служебный токен и роль администратора не дают исключения.
2. Сначала проверяются права доступа и существующая блокировка повторного запуска профиля. Затем проверка свободного места и его резервирование выполняются атомарно, до запуска браузера. Два одновременных запроса не должны занять одно последнее место. При нескольких процессах сервера ограничитель должен быть общим, а не отдельным счётчиком в каждом процессе.
3. При исчерпании мест новый запуск отклоняется без создания браузерного процесса. Панель показывает понятную ошибку, например: «Достигнут общий лимит одновременно активных профилей (10). Остановите один из доступных вам профилей и повторите запуск либо обратитесь к администратору». В сообщении используется фактическое настроенное значение; чужие профили и пользователи не раскрываются. API / MCP возвращают распознаваемую ошибку ограничения, а не общий сбой запуска.
4. Автоматической очереди ожидания в первой реализации нет. После освобождения места запуск нужно повторить. Для массового запуска проверить права на весь набор, затем атомарно зарезервировать нужное число новых мест. Если их не хватает, отклонить весь запрос до запуска новых профилей; не запускать случайную часть набора. Поведение для уже работающего профиля сохраняется согласно существующему API; второй слот для него не выделяется.
5. После штатной остановки или подтверждённого падения браузера место освобождается. При ошибке / отмене / тайм-ауте запуска убрать резерв после завершения созданной сессии; не освобождать место, оставляя реально работающий браузер без учёта. Повторная обработка завершения не должна освобождать место дважды.
6. После перезапуска менеджера сверить учёт с фактически живыми браузерными сессиями до разрешения новых запусков. Удалить устаревшие резервы, но не считать живые профили остановленными только потому, что счётчик в памяти сбросился.
7. Уменьшение лимита ниже текущей занятости не останавливает работающие профили принудительно. Новые запуски запрещены, пока занятость не станет меньше лимита. Увеличение лимита позволяет следующие запуски без перезапуска браузеров.

Не добавлять в рамках этого требования персональные квоты, приоритеты пользователей, автоматическое вытеснение или остановку чужих профилей. Значение 10 — выбранный дефолт, а не гарантия, что конкретному VPS хватит ресурсов для десяти браузеров.

## 3. Изменения в существующей панели

### 3.1. Пользовательский интерфейс

После персонального входа пользователь видит обычную полноценную панель управления профилями, но только со своими / назначенными профилями.

У доступных профилей остаются существующие кнопки запуска, остановки, Viewer, настройки, прокси, fingerprint, импорта и экспорта cookies, удаления и прочих разрешённых операций. Не заменять текущую панель урезанным экраном «Запустить / Посмотреть».

Не показывать пользователю:

- административный раздел пользователей и назначения доступа;
- глобальные настройки сервера, MCP и служебные ключи;
- чужие профили, их прокси, cookies, скриншоты и другие данные.

Поиск, фильтры, списки запущенных профилей, счётчики, группы и связанные журналы должны учитывать доступ пользователя. Скрытие профиля в основной таблице недостаточно, если его можно найти через поиск, общую статистику или другой экран.

При отказе в запуске из-за общего лимита показать пользователю сообщение из раздела 2.4 без списка чужих профилей. Ограничение запуска не должно блокировать Viewer, остановку или другие разрешённые операции над уже работающими профилями.

### 3.2. Административный интерфейс

Администратор видит все профили и существующие глобальные настройки. Добавляется раздел **«Пользователи»** с минимальным набором действий:

- создать пользователя и установить / сбросить его пароль;
- выбрать роль `admin` или `user`;
- отключить пользователя;
- назначить ему профили и отозвать назначения.

Выбор профилей можно сделать обычным списком с поиском и галочками. Не нужен отдельный сложный интерфейс управления разрешениями.

Для глобальных настроек MCP и других параметров использовать существующие разделы FoxProfile, где они есть. Это задание не предполагает создание новой панели конфигурации для всех параметров, которые сейчас доступны только через файлы или переменные окружения.

Для общего лимита добавить в административную панель поле **«Максимум одновременно активных профилей»** со значением **10** по умолчанию, сохранением и серверной валидацией. Рядом показывать общую занятость, например «Занято 7 из 10», включая зарезервированные / выполняющиеся запуски. У обычного пользователя поля изменения лимита нет. Если администратор снижает значение ниже текущей занятости, предупредить, что действующие сессии сохранятся, но новые запуски будут временно запрещены.

### 3.3. Источник прав для интерфейса

Панель получает текущего пользователя и его роль от сервера. Роль в состоянии фронтенда нужна только для отображения; изменение её в браузере не должно давать дополнительные права.

Список профилей должен приходить уже отфильтрованным сервером. Не загружать все профили с секретами в браузер пользователя, чтобы затем скрывать лишние средствами JavaScript.

## 4. Минимальная модель данных

Использовать существующее хранилище проекта, если оно подходит. Не добавлять отдельную инфраструктуру без необходимости.

```text
User
  id
  username
  password_hash
  role: admin | user
  active

UserProfileAccess
  user_id
  profile_id

Session
  идентификатор пользовательской сессии
  user_id
  срок действия / сведения для отзыва

GlobalSettings
  max_concurrent_profiles: integer, default = 10, min = 1
```

Глобальный лимит хранится в конфигурации установки, а не в настройках пользователя или браузерного профиля. Учёт занятых мест и резервов относится к жизненному циклу браузеров; конкретный механизм выбрать по текущей архитектуре, соблюдая атомарность и восстановление из раздела 2.4.

`UserProfileAccess` — связь пользователя с профилем. Наличие связи означает полный доступ к этому профилю. Администратор имеет доступ ко всем профилям независимо от таких записей.

Использовать стабильный внутренний идентификатор профиля, а не его отображаемое имя. Переименование профиля не должно терять или менять назначения.

Создание / импорт профиля и назначение создателю должны выполняться согласованно. Пользователь не может подменить владельца, получателя доступа или роль через дополнительные поля запроса. Назначения меняет только администратор.

Если в дальнейшем один профиль будет назначен нескольким пользователям, каждый из них получит одинаковый полный контроль, в том числе право удалить профиль для всех. Это прямое следствие выбранной простой модели; отдельные ограничения совместного доступа в первую версию не входят.

## 5. Авторизация на сервере

### 5.1. Общие правила

```text
Нет действующей авторизации → отказ.

Глобальная административная операция:
  admin → разрешить;
  user → отказать.

Операция с существующим профилем:
  admin → разрешить;
  есть назначение user → profile → разрешить;
  иначе → отказать.

Создание нового профиля пользователем:
  создать профиль;
  назначить его текущему пользователю на сервере.
```

Проверки должны быть централизованными и применяться до чтения или изменения защищённых данных. Не размножать независимые проверки роли по десяткам обработчиков, если проект позволяет использовать общий слой авторизации.

### 5.2. Что обязательно защитить

Проверить все пути доступа, а не только кнопки панели:

| Поверхность | Требование |
|---|---|
| Списки, поиск, состояние профилей | Возвращать только разрешённые профили |
| Настройки, запуск, остановка, удаление | Проверять доступ к целевому профилю; перед новым запуском применять общий лимит |
| Импорт / экспорт cookies и полных профилей | Проверять доступ до обработки или выдачи файла |
| Viewer, скриншоты и потоки изображения | Проверять доступ к профилю |
| Клики, клавиатура, прокрутка, навигация и вкладки | Проверять доступ к профилю, которому принадлежит браузерная сессия |
| Прокси, fingerprint, состояние и журналы профиля | Не выдавать данные чужих профилей |
| Глобальные настройки, пользователи, назначения, служебные ключи | Только администратор |
| Массовые операции | Проверять каждый профиль до выполнения операции |

`tab_id`, `browser_id`, идентификатор Viewer-сессии или ссылка на экспорт не должны обходить проверку профиля. Связь этих объектов с профилем определяет сервер, а не доверенное поле клиентского запроса.

Для массового запроса с хотя бы одним недоступным профилем рабочее правило первой версии — отклонить весь запрос до выполнения изменений. Не допускать частичного выполнения до обнаружения запрещённого объекта.

Для чужого профиля допустим единообразный ответ «не найден / недоступен» без раскрытия его имени, прокси или других данных.

### 5.3. Отзыв доступа

Отключение пользователя или отзыв назначения должны прекращать доступ и для уже открытой панели.

Следующая команда Viewer или API-запрос после отзыва должны быть отклонены. Если используется постоянное соединение для передачи изображения, его также нужно закрыть либо прекратить передачу защищённых данных. Проверки только при первоначальном открытии Viewer недостаточно.

Не требуется останавливать сам браузер при отзыве доступа: администратор и агент могут продолжить работу с ним. Отзывается доступ пользователя, а не состояние браузерного профиля.

## 6. Персональный вход и служебный доступ MCP

### 6.1. Пользовательский вход

Добавить или переиспользовать персональную авторизацию: отдельный логин и пароль для каждого пользователя, серверная сессия, выход и возможность отзыва сессий.

Пароли хранить только в виде стойких хешей с использованием проверенного механизма. При cookie-авторизации применять защиту cookies и запросов изменения состояния; при публичном доступе использовать HTTPS. Не писать пароли, cookies сайтов и служебные ключи в журналы.

Самостоятельная регистрация не нужна: пользователей создаёт администратор. Система восстановления через email также не обязательна; для первой версии достаточно сброса пароля администратором.

### 6.2. MCP и агент

Для текущего сценария агенту можно оставить отдельный доверенный служебный доступ ко всем профилям. Пользовательские MCP-аккаунты и отдельные права агента на каждый профиль не требуются. Служебный доступ не обходит общий лимит одновременно активных профилей: агент занимает те же места, что и пользователи панели, и получает ошибку при исчерпании лимита.

Пользователь входит в панель под своим логином и не получает общий служебный токен. Глобальную конфигурацию MCP и служебного доступа меняет только администратор.

Если текущая реализация FoxProfile использует один общий токен для панели, REST API и MCP, нужно разделить пользовательские сессии и доверенную служебную авторизацию. Нельзя подставлять общий токен в запросы пользовательской панели: это превращает пользователя в администратора независимо от скрытых кнопок.

Служебный токен не должен попадать в HTML, JavaScript-конфигурацию, ответы API или браузерное хранилище обычного пользователя.

## 7. Прокси, файловые операции и другие границы доступа

Пользователь должен иметь возможность задавать и изменять реквизиты прокси своих профилей. Если в FoxProfile есть общая библиотека прокси, нельзя автоматически раскрывать через неё все чужие реквизиты. Исполнитель должен проверить, как она устроена, и либо ограничить её видимость, либо оставить пользователю редактирование прокси непосредственно в доступном профиле.

Право изменять настройки профиля не означает право менять произвольные системные пути, каталоги других профилей, служебные порты или настройки всего сервера. Служебные поля не должны приниматься от пользователя как обычные настройки профиля.

Импортированные архивы и настройки не должны назначать права доступа, менять роль пользователя или записывать данные за пределами разрешённого каталога профиля. Экспорт пользовательского профиля не должен включать системные токены, данные пользователей или файлы других профилей.

## 8. Сохранение существующего поведения

Разграничение доступа не должно менять браузерное окружение и жизненный цикл профилей без необходимости.

Обязательные условия:

- назначение / отзыв доступа не сбрасывают cookies, fingerprint, прокси и данные сайтов;
- существующие профили и авторизация сохраняются после миграции;
- права и пользователи сохраняются после перезапуска FoxProfile / VPS;
- открытие Viewer пользователем не создаёт вторую копию уже запущенного профиля;
- ручная работа и агент используют ту же запущенную сессию в рамках существующих возможностей FoxProfile;
- не снимаются существующие блокировки от одновременного запуска одного профиля;
- изменение fingerprint или других настроек выполняется только по явному действию пользователя, а не из-за смены владельца или входа в панель.

Механизм согласования одновременных действий человека и агента не является новой задачей этого ТЗ. Не ухудшать текущую работу, но не разрабатывать отдельный диспетчер управления браузером в рамках добавления ролей.

## 9. Миграция и первый администратор

Предусмотреть безопасное создание первого администратора через существующий механизм настройки проекта либо одноразовую серверную команду. Не добавлять постоянный публичный маршрут, позволяющий назначить себя администратором.

После миграции:

1. Все существующие профили доступны администратору.
2. Обычные пользователи получают доступ только после назначения.
3. Служебный доступ агента сохраняется при корректной конфигурации и не раскрывается пользователям.
4. Профили без назначенных пользователей остаются доступными администратору.
5. Нельзя отключить или понизить роль последнего активного администратора.
6. Если настройка общего лимита отсутствует, установить значение **10**. Уже сохранённое допустимое значение не перезаписывать. Если живых профилей больше установленного лимита, не завершать их принудительно; запретить новые запуски до освобождения мест.

Перед миграцией сделать резервную копию данных приложения и закрытых браузерных профилей. Проверку сначала выполнять на тестовой установке / копии данных, а не на единственном экземпляре рабочих Pinterest-сессий.

## 10. Приёмочные проверки

Подготовить администратора, пользователей A и B и профили PA и PB. Назначить PA только пользователю A, PB — только пользователю B. Для проверки лимита подготовить не менее 11 тестовых профилей с распределёнными назначениями; не использовать единственные копии рабочих Pinterest-сессий.

| № | Проверка | Ожидаемый результат |
|---|---|---|
| 1 | Вход без авторизации, прямой запрос к API или Viewer | Защищённые данные недоступны |
| 2 | Пользователь A открывает список, поиск, список запущенных профилей | Видит PA и не видит PB |
| 3 | A запускает / останавливает PA, открывает Viewer | Операции работают |
| 4 | Агент или администратор заранее запускает PA; A открывает Viewer | Открывается та же сессия без второго запуска |
| 5 | A изменяет настройки PA, прокси и fingerprint | Операции доступны; изменения сохраняются |
| 6 | A импортирует и экспортирует cookies PA | Операции доступны |
| 7 | A удаляет свой тестовый профиль | Удаление разрешено и не затрагивает чужие данные |
| 8 | A вручную подставляет идентификатор PB в запрос чтения / изменения / удаления / экспорта | Доступ запрещён для каждого вида операции |
| 9 | A использует идентификатор чужой вкладки, скриншота или Viewer-сессии | Доступ к PB не появляется |
| 10 | A открывает административный маршрут или вызывает его API напрямую | Доступ запрещён независимо от интерфейса |
| 11 | A меняет роль или получателя доступа в запросе / состоянии фронтенда | Сервер не повышает права и не меняет назначения |
| 12 | A отправляет массовый запрос с PA и PB | Запрос отклонён до изменений |
| 13 | Администратор отзывает PA у A при открытом Viewer | Новые команды и передача защищённых данных прекращаются |
| 14 | Администратор отключает A | Действующие сессии A теряют доступ; профиль сохраняется |
| 15 | A создаёт / импортирует новый профиль, если операция поддерживается | Профиль назначается A; B его не видит |
| 16 | Администратор выполняет операции с PA и PB, меняет назначения и глобальные настройки | Операции доступны |
| 17 | Перезапуск сервиса и повторный вход | Пользователи, назначения и браузерное состояние сохранены |
| 18 | Проверка ответов панели, конфигурации и экспортов пользователя | Нет общего служебного токена и чужих данных |
| 19 | Проверка MCP / автоматизации после доработки | Доверенный агент продолжает работать с нужными профилями |
| 20 | Попытка отключить / понизить последнего администратора | Операция запрещена |
| 21 | Чистая установка / миграция без сохранённого лимита | Общий лимит равен 10; число сохранённых остановленных профилей не ограничивается им |
| 22 | Суммарно заняты 10 мест через панель, API и MCP; запросить ещё один запуск каждым из способов, в том числе от администратора | Все новые запуски отклонены; дополнительных браузеров нет |
| 23 | При 9 занятых местах одновременно запросить запуск двух разных профилей | Ровно один запрос занимает последнее место; общая занятость не превышает 10 |
| 24 | Все 10 мест заняты работающими или запускающимися профилями; открыть Viewer своего работающего профиля | Viewer и ручные действия доступны без нового места; повторное подключение не увеличивает счётчик |
| 25 | При занятом лимите штатно остановить профиль; отдельно проверить падение браузера и ошибку / отмену / тайм-аут запуска | Место освобождается после подтверждённого завершения сессии; утечки резервов и двойного освобождения нет; следующий запуск доступен |
| 26 | Пользователь пытается изменить лимит через прямой API-запрос; администратор задаёт 0, отрицательное или нецелое значение | Пользователю отказано; недопустимые значения отклонены без изменения настройки |
| 27 | Администратор меняет лимит с 10 на 12, затем перезапускается сервис | Сохранено 12; все способы запуска используют новое значение |
| 28 | При 10 активных профилях администратор снижает лимит до 6 | Работающие профили сохраняются; новые запуски запрещены до занятости меньше 6 |
| 29 | При 9 занятых местах массово запросить запуск двух новых доступных профилей | Весь запрос отклонён до запуска; ни один из двух новых профилей не стартует |
| 30 | Перезапуск менеджера при живых браузерных сессиях и устаревших резервах | Учёт восстановлен по фактическому состоянию; живые сессии учитываются, устаревшие резервы удалены; лимит нельзя обойти перезапуском |

Проверки доступа выполнять не только через UI, но и прямыми запросами к серверу. Автоматические тесты должны покрывать серверную матрицу доступа, общий лимит, конкурентные запуски и освобождение мест; ручные — видимость элементов панели, работу Viewer и административную настройку лимита. Тесты конкурентности выполнять и для нескольких серверных процессов, если такая конфигурация поддерживается установкой.

## 11. Порядок реализации для агента

1. Проверить исходники: авторизацию, хранение профилей, маршруты панели / API / Viewer / MCP, экспорт и импорт, общие настройки. Составить перечень фактических точек доступа.
2. Использовать существующие подходящие механизмы проекта; добавить пользователей, назначения и миграцию только там, где их нет.
3. Реализовать персональный вход и единый слой проверки административных операций и доступа к профилю.
4. Применить проверки ко всем найденным точкам доступа, включая альтернативные идентификаторы и постоянные соединения Viewer.
5. Добавить сохраняемую глобальную настройку `max_concurrent_profiles` с дефолтом 10 и общий атомарный ограничитель для всех путей запуска; обеспечить освобождение мест и восстановление учёта после сбоев.
6. Доработать текущую панель: серверная фильтрация профилей, скрытие админских разделов, минимальное управление пользователями и назначениями, административное поле общего лимита и понятная ошибка для пользователя.
7. Проверить приёмочные сценарии, миграцию и отсутствие регрессий в автоматизации. Документировать создание администратора, назначение профилей, служебный доступ агента и поведение общего лимита.

Не начинать с полного переписывания фронтенда, браузерного API или хранилища профилей. Цель — минимальная целостная доработка текущего FoxProfile.

## 12. Что не входит в задачу

Не требуются организации, команды, биллинг, персональные квоты, сложная иерархия ролей, конструктор разрешений, SSO, отдельная панель для сотрудников, отдельные установки FoxProfile на каждого сотрудника и пользовательский MCP с собственной матрицей прав. Общий лимит одновременно активных профилей с дефолтом 10 входит в задачу; очередь ожидания, приоритеты и автоматическое вытеснение профилей — нет.

Не входят также перенос на другой менеджер, реализация noVNC, доработка антидетект-движка, скриптов Pinterest-прогрева или паблишера, а также обещания обхода проверок платформы. Ручное прохождение капчи через существующий Viewer остаётся обычным действием пользователя.

Полноценная система аудита действий сотрудников не согласована как обязательная часть первой версии. При сохранении существующих журналов необходимо исключить раскрытие чужих данных и секретов.

## 13. Критерий готовности

**Администратор управляет всей установкой, пользователями и назначениями. Пользователь работает в привычной панели FoxProfile, видит только доступные ему профили и имеет над ними полный контроль. Ни скрытые кнопки, ни подстановка идентификатора, ни прямой запрос к API / Viewer не позволяют получить доступ к чужим профилям или глобальным настройкам. Работа служебного агента и сохранность браузерных сессий не нарушены. Все пути запуска соблюдают общий настраиваемый лимит, по умолчанию 10, с учётом запускающихся профилей; Viewer уже запущенной сессии не занимает дополнительное место.**
